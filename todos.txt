- Enforced proof fixtures are the regression baseline; informational fixtures

## Current architectural project: ProofContext integration

The goal is to make `ProofContext` the authoritative lexical environment used
by elaboration, while keeping theory configuration in `TheoryEnvironment` and
keeping proof validation in the kernel.

Target architecture:

    surface proof
        -> elaboration + ProofContext
        -> elaborated core entries
        -> ProofLogic validation

`ProofContext` should own proof-local visibility. The kernel should not rebuild
lexical scope from separate declaration/label bookkeeping.

### Phase 1 implementation notes

Implemented on `master` in commits `d2ded74` and `fdd74af`.

`ProofContext` now has five explicitly separated categories of state:

- declarations;
- proof-line labels;
- theorem/lemma bindings;
- assumptions plus a label index;
- arbitrary/fresh bindings.

The previous `_already_visible()` global collision rule has been removed. Each
binding operation now checks only the namespace whose semantics it owns. Labels
and labeled assumptions intentionally share the proof-reference namespace.
Unlabeled assumptions are stored directly in insertion order rather than under
synthetic names such as `__assumption_0`.

`enter_subproof()` is an explicit alias for creating a child lexical context.
The existing inheritance/non-leakage behavior is preserved.

The phase-1 tests document the intended namespace policy and preserve the
scope invariants needed by the later elaboration migration.

Phase 1 does **not** yet make elaboration use `ProofContext`; that is the next
phase. The existing elaborator's separate state must remain in place until the
migration is completed and covered by end-to-end regression tests.

### Phase 2 implementation notes

`_ElaborationContext` (`source/ProofParser.py`) now holds a `ProofContext`
instance (`self.context`), seeded from `self.declarations.declarations_here()`
rather than `environment.declarations` directly, so vocabulary reachable
through more than one theory-extension path (e.g. `SetTheory`'s declarations,
visible both directly and through `NumberTheory`'s own extension of
`SetTheory`) doesn't raise a spurious `DuplicateBindingError` at seed time.

`register_declaration` dual-writes into `self.context.declare()` alongside
the pre-existing `self.declarations` (`DeclarationScope`). Coverage is
currently limited to declarations that already flow through
`register_declaration` -- i.e. `elaborate_compound_declaration`'s coordinated
`Let X be any set, R be a relation on X, ...` path.
`elaborate_typed_declaration` (the more common single-clause /
`DeclarationRecipe`-dispatch path, e.g. `Let x be a natural number`) builds
its own local declarations list and returns it in the justification tuple
without calling `register_declaration` at all, so declarations made that way
aren't yet reflected in `self.context`. This is a gap to close, not a
regression: `elaborate_typed_declaration` never populated `self.declarations`
either.

`elaborate_entry` dual-writes each label into `self.context.bind_label()`
alongside the pre-existing `self.formula_by_label`, with the same scope
boundary that structure already had: a standalone labeled subproof block
(`(label, 'subproof', body)`) is excluded, since its "value" isn't a formula.

New method `elaborate_subproof_body(entries)` gives every subproof -- however
it's attached (a standalone labeled block, a `rule_below` justification's
immediate subproof, or one of a `rule_hybrid` justification's several
attached subproofs) -- its own child `ProofContext` for the duration,
mirroring `ProofValidator._validate_block`'s own `declarations.child()`/
`labels.child()` scoping for the same construct. Only `self.context` is
scoped this way; `self.declarations`, `self.origin_by_label`, and
`self.formula_by_label` remain flat/global elaboration-time bookkeeping.

Two things discovered while implementing this, both open:

- `self.declarations` being flat (not yet subproof-scoped) means a compound
  declaration name reused across *sibling* subproofs still collides today --
  independent of anything `ProofContext`-related, and predating this
  migration. Labels don't have this problem anymore (`self.context` fixes
  it), but declarations still do. See
  `test_sibling_subproofs_cannot_yet_reuse_a_compound_declaration_name` (an
  intentional `xfail` in `pytest_tests/test_elaboration.py`, `strict=False`
  per `pytest.ini`, so it will surface as an unexpected pass rather than
  silently staying stale once fixed). Either give `self.declarations` the
  same child-context treatment as a small follow-up, or fold it into
  "resolve declaration and label references through the context" below,
  which will need to touch `self.declarations`'s scoping anyway.
- `ProofContext.bind_label` refuses to let a label shadow one already
  visible in an enclosing scope (see
  `test_each_namespace_rejects_duplicates_across_visible_scopes` in
  `test_proof_context.py`), while the kernel's own `LabelScope` currently
  *permits* that shadowing silently -- a child scope's local dict entry just
  overrides the parent's for lookups made from inside it, no error raised.
  No fixture in the current corpus shadows a label this way, so the
  dual-write is safe today, but this is a real policy divergence to settle
  deliberately, not by default, before `ProofContext` can drive citation
  resolution: either `LabelScope` should also forbid shadowing (plausibly
  the right call -- a proof shadowing a line label is far more likely a
  mistake than an intentional pattern), or `ProofContext` needs an explicit
  shadowing-permitted mode. Undecided; needs a call before "resolve ...
  references through the context" lands.

"Add end-to-end tests proving parent visibility and child non-leakage" is
partially covered. `test_sibling_subproofs_can_reuse_the_same_label` and
`test_declaration_inside_a_subproof_does_not_leak_into_the_enclosing_context`
(`pytest_tests/test_elaboration.py`) cover sibling isolation and
non-leakage, and were confirmed to actually fail without the child-context
fix (i.e. they're not vacuous). A dedicated "parent visibility" test at this
integration level isn't meaningfully possible yet: nothing in elaboration
currently *reads* from `self.context`, so there's nothing for such a test to
exercise beyond `ProofContext.child()`'s own inheritance, which
`test_proof_context.py` already covers directly. Revisit once "resolve ...
references through the context" gives elaboration an actual reason to look
something up through an inherited scope.
