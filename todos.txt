## Project status

The project is functionally green, with one known, tracked exception. The
core proof-language pipeline has been validated against the repository's
full regression suite:

- 531 Python tests; 529 pass, 1 skipped, 1 known failure (see "Known issues"
  below). The skip is the parser-oracle test, which has nothing to check until
  `parse_oracle/` is merged (see item 4).
- all enforced proof fixture suites pass (48/48)
- informational proof fixtures: 48/49 pass (the one failure is the same
  known issue)

The current work is no longer about making the basics work. The remaining work
is about making the system cleaner, easier to extend, and easier to use.

## Design principles

- Most things beyond the level of pure logic should be sugar. Prefer surface
  syntax that desugars into core forms the kernel already understands --
  formulas, rules, subproof shapes -- over adding new kernel/AST primitives.
  Reserve real kernel changes for genuinely new logical primitives, not
  convenience notation around an existing idea. "Exists unique" is the first
  applied case: planned as sugar expanding to the ordinary
  `exists Y, (P(Y) and forall X, (P(X) -> X = Y))` form (see "Uniqueness,
  N, M" below), not a new `ExistsUnique` AST node.

## Current direction

The canonical architecture is:

```text
proof text
    -> surface syntax / parser
    -> elaboration
    -> core proof entries
    -> ProofLogic validation
```

The parser/elaboration stack remains the main public entry point, and
`ProofContext` is now the authoritative lexical-scoping layer during elaboration
for declarations, labels, assumptions, and arbitrary/fresh bindings.

Kernel validation deliberately uses its own `LabelScope` and `DeclarationScope`.
These are not a second elaboration environment: they operate after elaboration
on already-constructed proof entries and are the validation-time authority for
reference and declaration visibility. Their overlapping scope semantics are
kept equivalent by regression tests rather than by making the kernel depend on
`ProofContext`.

### 5. ZFC axiom citations and derived rules for set theory

Design agreed while working through the user's own "Unique pairing" proof
(`tests/setTheoryProofs/zfc_remaining_axioms.txt`). The unchecked items below
are not implemented yet -- this is the agreed design, written down so
implementation can proceed later without re-litigating it. Do not start
implementing the rules without an explicit go-ahead.

- [x] Witness naming for axiom instances (decided: sugar, not a context-aware
      citation). `Let Y be such a set. (Existence from L)` extends the
      existing `Define NAME = ... (Existence from L)` sugar: it declares Y
      through the ordinary scoped declaration pathway and states L's
      existential body instantiated at Y, so Y lasts to the end of its
      nesting level and is invisible outside the subproof. Axiom citations
      themselves stay ordinary existential formulas. Covered in
      `pytest_tests/test_set_property.py` and proof 5 of
      `tests/setTheoryProofs/pairing_theorems.txt`. Caveat: like `Define`,
      the elaborator checks that L is an existential and the kernel sees the
      line as a premise-tagged declaration, not an Existential Elimination
      step it re-validates; wrapping in a real elimination subproof would
      make the kernel check it, at the cost of nesting later lines.
      Decided: the "Unique pairing" proof introduces both of its sets this way
      (`Let Y be such a set. (Existence from 2)`, `Let X be any set.
      (Declaration)`), rather than having the checker supply the names
      implicitly (the axiom citation introducing Y, the conditional
      introducing X).

- [ ] Axiom citations as named, shape-checking rules.
      Replace the `SET_AXIOMS` formula list plus generic "(Axiom)" citation
      (which requires restating the axiom verbatim) for Pairing, Union, Power
      Set, and Infinity with four named, zero-premise `InferenceRule`
      subclasses (e.g. `PairingAxiomRule`, `UnionAxiomRule`,
      `PowerSetAxiomRule`, `InfinityAxiomRule`), following the shape-checking
      pattern already used by `SeparationSchemaRule` / `ReplacementSchemaRule`.
      Each is cited by name -- `(Axiom of pairing)`, etc. -- against a
      specific instance shape, never a restated formula. Each should also
      bundle its own fresh-witness check (the way `ExistentialEliminationRule`
      checks freshness), since the proof style names the new set directly off
      the axiom citation (`There is a set Y = {a, b} ... (Axiom of pairing)`)
      rather than citing existence and then doing a separate Existential
      Elimination.
      Decided (scope): the new set is an ordinary declaration at the nesting
      level of the citing line. It stays in scope for the rest of that level,
      including nested subproofs below it, and is invisible outside the
      subproof it was introduced in -- the same rule `ProofContext` already
      applies to declarations, so no special scoping is needed.
      Decided (what the citation records): the line does not have to restate
      the instance formula. It introduces the set together with its defining
      property (for pairing, membership iff equal to a or to b), and
      `Set property` (below) is what later retrieves that property. The rule
      itself only checks that the stated set has the shape the axiom allows.

- [ ] WLOG as a subproof-copying rule.
      Confirmed design: `(WLOG)` closes a subproof, the way
      `ExistentialEliminationRule` / `DisjunctionEliminationRule` do, rather
      than standing alone as a one-line citation. On a WLOG citation, the
      checker copies the cited subproof, substitutes the untaken disjunct's
      term for the taken one throughout (reusing
      `_substitute_constants_in_formula`), re-applies the identical rule
      citations line by line, and validates each exactly as usual
      (`applies()`) against the substituted formulas. Decided (behavior): the
      author proves one chosen disjunct; the checker confirms the same proof
      works for each of the other disjuncts. Still needs a concrete
      surface syntax for delimiting the WLOG subproof before implementation
      starts.

- [x] (Partly done.) General `Set property` -- `SetPropertyRule`, cited as
      `Set property from N, M` or `Set property, N, M` (bare `Set property`
      is still the empty-set rule). From a membership characterization
      `forall u, (In(u, S) <-> P(u))` and an instance of one side at a term
      t, it derives the other side at t, positive and negated, in either
      citation order. It knows nothing about which set it is; tested on
      pair, union and power-set style properties, with near-miss rejections,
      in `pytest_tests/test_set_property.py`, and used in four realistic
      proofs in `tests/setTheoryProofs/pairing_theorems.txt`. Bare
      zero-citation names like `(Axiom of pairing)` now resolve through the
      alias/placeholder table. Still open: the optional equality citation M
      (substituting an equality while instantiating), and the witness-naming
      axiom citation (see the first item). Note `PairingAxiomRule`,
      `UnionAxiomRule`, `PowerSetAxiomRule` and `InfinityAxiomRule` already
      exist in `SetTheory.py` as formula-shape rules; what is not built is
      the form that introduces the named set directly off the citation.
      Original design note, kept for the open part:
- [ ] Generalize `Set property` to `Set property, N[, M]`.
      `EmptySetPropertyRule` only knows the empty set's defining property.
      The general form needs to look up a membership-defining biconditional
      from a cited line N (an axiom citation, or an elaborated "contains
      exactly P and Q" assumption) and instantiate it, optionally
      substituting an equality from a cited line M. The citation should name
      the instantiation witness explicitly; the checker shouldn't guess it.
      Decided: every set has a defining property, which `Set property`
      checks. For a set with no stated property (e.g. "Let X be any set"),
      the property is symbolic, i.e. just its own membership predicate.

- [ ] `Uniqueness, N, M` as sugar.
      Expands to the ordinary `exists Y, (P(Y) and forall X, (P(X) -> X = Y))`
      form, reusing `ExistentialIntroductionRule`'s witness-to-bound-variable
      generalization technique, rather than becoming a new `ExistsUnique`
      core connective. First applied case of the sugar principle above.

- [x] Plain syntax gaps surfaced by the same proof, and the parsing pass that
      followed. All of it is sugar that desugars to ordinary formulas (nothing
      new in the kernel or the AST), implemented in `SetTheory.py` and
      `ProofParserPolicy.py` and covered by
      `pytest_tests/test_set_enumeration_syntax.py` and
      `pytest_tests/test_set_phrase_parsing.py`:
      - `{a, b}` enumeration, accepted only next to a relation (`Y = {a, b}`,
        `x is in {a, b}`), never as a free-standing term or an argument;
      - set-builder notation: `Y = {u in X: P(u)}`, `Y = {y: P(y)}`,
        `Y = {F(x): x in X}` (extra conditions after `and` or a comma, and
        several ranges), and `z is [not] in {u in X: P(u)}`;
      - `S contains exactly a, b and c` (any number of names);
      - "x is a or b" / "x is a, b, or c" (single-letter names, optionally
        followed by digits, so "n is even or odd" stays an error), now also
        inside larger formulas ("Q(w) and w is h, i, j, or k");
      - `subseteq`, infix `subset` and "is a subset of": the same non-strict
        relation (no strict subset exists yet);
      - "a and b are sets", "Let X and Y be sets", "Let X, Y, and Z be any
        sets": multi-subject declarations;
      - natural-language existentials: `there exists x such that ...`,
        `there exists a [unique] [set] Y such that ... / that ... / = ... / , ...`.
        "unique" (or "exactly one") writes out the ordinary
        `exists Y, (P(Y) and forall Z, (P(Z) -> Z = Y))`, where Z is a variable
        not already in use; the braces in "a unique set {a, b} that ..." only label the witness;
      - citations written `Rule, 3, 3.2.1` and `Rule, 3.1 to 3.2` (a range
        gives its two endpoints) beside `Rule from 3, 3.2.1`; the names of
        planned rules (`Uniqueness`, `WLOG`, `Mutatis mutandis`) resolve to
        named placeholders;
      - a fixture's stated conclusion (`### then ...`) is compared with what
        the proof derived up to the names of bound variables
        (`ProofLogic._alpha_eq`).
      Mechanism: `TheoryEnvironment` has two new hooks. `phrase_parsers` gets
      the whole string before the grammar splits it, for a phrase that
      contains a connective. `phrase_spans` finds such phrases *inside* a longer
      string and fences them off before the split ("Q(w) and w is h, i, j, or k"
      is read as "Q(w) and (w is h, i, j, or k)").
      Known limits: a phrase that runs into a bare name is ambiguous English.
      "S contains exactly a and b and Q" takes `Q` as a third name, and
      "x is a or b" is read greedily; parenthesize to end the phrase. A
      natural-language existential after `and`/`or` takes the rest of the
      formula (up to a `then`), while a symbolic `exists x, BODY` there still
      stops at the next connective, as before. Existentials accept one-word
      kinds only ("an integer n"); "a natural number n" is refused with the
      list of supported forms, since no phrase for it exists yet. Found but
      deliberately left alone: declaration descriptors swallow a following
      " a ..." (`Let X be any set, a in X` gives X a garbage `type_name`), and
      the `type_name` wording differs between declaration paths.

- [ ] Bounded quantifiers (proposed; not started). Found by checking the nine
      axiom statements at the top of `zfc_remaining_axioms.txt`: Axiom 1 says
      "for all a in X we have a in Y", and no bounded form parses today
      (`forall a in X, ...`, `exists a in X such that ...`). They are sugar,
      and could live in set theory, since they use `In`: `forall a in S, P`
      is `forall a, (a in S -> P)` and `exists a in S, P` is
      `exists a, (a in S and P)`, with the English spellings "for all a in S
      we have P" and "there exists a in S such that P". Open: which spellings
      to accept, and whether a `### then` clause wrapped over two lines (as in
      that Axiom 1) should be joined -- today, in a numbered proof, only its
      first line is read, so the stated-conclusion check is skipped with a
      warning. The nine `# Axiom N` statements themselves are comments (the
      runner reads only numbered `# N:` blocks). Most are informal ("P is a
      property with parameter p", "choice function"), and Axiom 4's
      `{u in U: U in X}` leaves U free, so it cannot stand for the union as
      written.

- [ ] Infinity axiom. Decided: the axiom introduces a set I whose defining
      property is an abstract, unspecified property P(x) -- x is in I iff
      P(x) -- the same way every set has a defining property (for {1, 2} it
      is "x = 1 or x = 2"; for an abstract set X it is just some P). The
      axiom then separately asserts, as a fact about I rather than as its
      defining property, that I is infinite. "Finite" is defined as: A is
      finite iff there is an n and a bijective function from {0, ..., n-1}
      to A. "Infinite" means not finite. The rule itself needs none of that
      vocabulary; unfolding the definition does.
      Decided (where numbers and functions live): set theory is meant to be
      the root of everything, so `SetTheory.py` must not depend on
      `NatThry.py` or `NumberTheory.py`, and it should not be assumed they
      will stay independent siblings of it. The definition of "finite" is
      therefore stated in the metatheory: a natural number there is a
      Python nonnegative integer, and a function is a symbolic object with a
      domain and a codomain.
      Known risk, to revisit only when a concrete proof hits it: quantifying
      over Python integers ("there is an n") is not an object-language
      quantifier, so "finite" and "infinite" may only be usable one numeral
      at a time unless some form of quantification over metatheory integers
      is added. Not needed until the syntax and the other three axiom rules
      exist.

- [ ] Implementation order (decided): syntax gaps first (done, see above),
      then the axiom rules. Do not start the rules until given an explicit
      go-ahead.

- [ ] Mutatis mutandis (deferred -- larger, separate project).
      Confirmed to be a real, checkable rule: given two parallel subproofs of
      the same shape, it swaps *which cited line plays which role* (e.g. the
      line supplying the disjunct fact and the line supplying the membership
      conclusion trade places), rather than substituting terms. Bigger and
      less well-specified than the items above; needs its own design pass and
      does not block them.

## Short version

What matters now is not "can we get proof checking to work at all?" It is:

- preserve the established boundary between elaboration-time `ProofContext`
  and validation-time kernel scopes;
- keep the proof corpus green (see "Known issues" for the one current
  exception) while improving maintainability;
- extend the theory surface in a disciplined way, preferring sugar over
  kernel changes where possible;
- document the public story for users and contributors.

## Notes for contributors

- `./run_tests.sh` is the canonical local regression command.
- New surface syntax gets cases in `parse_oracle/` (see item 4) as well as
  unit tests; write the `expect` side in plain logic, from the intended
  reading, and treat a disagreement as either a parser bug or a misreading.
- The enforced fixtures are the baseline. Informational fixtures are useful for
  broadening examples, but the enforced corpus remains the correctness floor.
- Any new theory feature should fit the pattern: theory environment + declaration
  recipe + rules + examples, rather than custom branches in the generic parser.
- New rules and syntax get a written design in this file before implementation
  starts -- see "Design principles" and the open design items under
  "High-priority work".
