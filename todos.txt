## Current architectural project: ProofContext integration

The goal is to make `ProofContext` the authoritative lexical environment used
by elaboration, while keeping theory configuration in `TheoryEnvironment` and
keeping proof validation in the kernel.

Target architecture:

    surface proof
        -> elaboration + ProofContext
        -> elaborated core entries
        -> ProofLogic validation

`ProofContext` should own proof-local visibility. The kernel should not rebuild
lexical scope from separate declaration/label bookkeeping.

### Phase 1 — context API and scope semantics

- [x] Define explicit namespaces rather than treating all identifiers as one
      global namespace.
- [x] Keep declarations in a vocabulary namespace and forbid declaration
      shadowing across visible scopes.
- [x] Keep theorem/lemma names in their own namespace.
- [x] Keep arbitrary/fresh bindings in their own namespace.
- [x] Make proof-line labels and labeled assumptions share a proof-reference
      namespace.
- [x] Replace synthetic assumption dictionary keys with ordered assumption
      storage plus an explicit label index.
- [x] Add an explicit `enter_subproof()` scope operation while retaining
      `child()` as the primitive.
- [x] Add regression tests for namespace independence, duplicate detection,
      assumption ordering, label collisions, and nested-scope behavior.

### Phase 1 implementation notes

Implemented on `master` in commits `d2ded74` and `fdd74af`.

`ProofContext` now has five explicitly separated categories of state:

- declarations;
- proof-line labels;
- theorem/lemma bindings;
- assumptions plus a label index;
- arbitrary/fresh bindings.

The previous `_already_visible()` global collision rule has been removed. Each
binding operation now checks only the namespace whose semantics it owns. Labels
and labeled assumptions intentionally share the proof-reference namespace.
Unlabeled assumptions are stored directly in insertion order rather than under
synthetic names such as `__assumption_0`.

`enter_subproof()` is an explicit alias for creating a child lexical context.
The existing inheritance/non-leakage behavior is preserved.

The phase-1 tests document the intended namespace policy and preserve the
scope invariants needed by the later elaboration migration.

## Phase 2 — integrate ProofContext into elaboration

### Current progress

Phase 2 is being developed on the isolated `phase-2-proof-context` branch.
The branch intentionally has not modified `master`.

Completed groundwork:

- [x] Add a small `ProofElaborationContext` bridge from
      `TheoryEnvironment.declarations` to a root `ProofContext`.
- [x] Add `root_context_from_environment()` so theory configuration remains
      separate from lexical proof state.
- [x] Add `ElaborationLexicalState`, a thin adapter whose `context` is the
      sole lexical authority and which exposes child-scope, declaration, and
      label operations needed by the parser migration.
- [x] Add tests for root environment seeding, declaration lookup, label
      binding/lookup, and child-scope inheritance/non-leakage.

Current implementation commits on this branch include `315a729`, `398fe1d`,
`323d2f8`, `fc97c6c`, and `febb10c`. These commits are preparatory; they do
not yet make `_ElaborationContext` in `ProofParser.py` use the new adapter.

The next implementation step is deliberately narrow:

- [ ] Put an `ElaborationLexicalState`/`ProofContext` instance directly into
      `_ElaborationContext`.
- [ ] Seed that state from the current `TheoryEnvironment` at elaboration
      start.
- [ ] Change `lookup_declaration()` and `register_declaration()` to delegate
      to the context, preserving current `ElaborationError` diagnostics.
- [ ] Register labels only after successful elaboration of a labeled line.
- [ ] Give each nested `SurfaceSubproof` a child lexical state.

After those changes are working, continue with assumptions, arbitrary
bindings, reference resolution, and end-to-end scope tests. Do not remove the
existing `DeclarationScope` or `formula_by_label` yet; they are compatibility
bookkeeping until the context-backed paths are proven equivalent.

### Phase 2 design constraints

- `TheoryEnvironment` remains the source of fixed theory resources; it is not
  folded into `ProofContext`.
- `ProofContext` is the sole authority for lexical visibility once elaboration
  enters a proof.
- `ElaboratedEntries` remains a result object and does not own lexical state.
- Existing source-origin metadata and core entry shapes must remain unchanged.
- Existing compatibility state may remain temporarily when it serves a
  genuinely different purpose, but it must not become a second authority for
  lexical visibility.
