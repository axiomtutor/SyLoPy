- The staged parser -> surface AST -> elaboration -> proof-kernel architecture is

- Enforced proof fixtures are the regression baseline; informational fixtures

## Current architectural project: ProofContext integration

The goal is to make `ProofContext` the authoritative lexical environment used
by elaboration, while keeping theory configuration in `TheoryEnvironment` and
keeping proof validation in the kernel.

Target architecture:

    surface proof
        -> elaboration + ProofContext
        -> elaborated core entries
        -> ProofLogic validation

`ProofContext` should own proof-local visibility. The kernel should not rebuild
lexical scope from separate declaration/label bookkeeping.

### Phase 1 implementation notes

Implemented on `master` in commits `d2ded74` and `fdd74af`.

`ProofContext` now has four explicitly separated categories of state
(originally five -- theorem/lemma bindings were removed in Phase 3, see
below):

- declarations;
- proof-line labels;
- assumptions plus a label index;
- arbitrary/fresh bindings.

The previous `_already_visible()` global collision rule has been removed. Each
binding operation now checks only the namespace whose semantics it owns. Labels
and labeled assumptions intentionally share the proof-reference namespace.
Unlabeled assumptions are stored directly in insertion order rather than under
synthetic names such as `__assumption_0`.

`enter_subproof()` is an explicit alias for creating a child lexical context.
The existing inheritance/non-leakage behavior is preserved.

The phase-1 tests document the intended namespace policy and preserve the
scope invariants needed by the later elaboration migration.

Phase 1 does **not** yet make elaboration use `ProofContext`; that is the next
phase. The existing elaborator's separate state must remain in place until the
migration is completed and covered by end-to-end regression tests.

### Phase 2 implementation notes

`_ElaborationContext` (`source/ProofParser.py`) now holds a `ProofContext`
instance (`self.context`), seeded from `self.declarations.declarations_here()`
rather than `environment.declarations` directly, so vocabulary reachable
through more than one theory-extension path (e.g. `SetTheory`'s declarations,
visible both directly and through `NumberTheory`'s own extension of
`SetTheory`) doesn't raise a spurious `DuplicateBindingError` at seed time.

`register_declaration` dual-writes into `self.context.declare()` alongside
the pre-existing `self.declarations` (`DeclarationScope`). Coverage is
currently limited to declarations that already flow through
`register_declaration` -- i.e. `elaborate_compound_declaration`'s coordinated
`Let X be any set, R be a relation on X, ...` path.
`elaborate_typed_declaration` (the more common single-clause /
`DeclarationRecipe`-dispatch path, e.g. `Let x be a natural number`) builds
its own local declarations list and returns it in the justification tuple
without calling `register_declaration` at all, so declarations made that way
aren't yet reflected in `self.context`. This is a gap to close, not a
regression: `elaborate_typed_declaration` never populated `self.declarations`
either.

`elaborate_entry` dual-writes each line into `self.context`, choosing the
binding that matches the line's own justification tag rather than always
calling `bind_label`: `'assume'` lines go through `self.context.assume(
formula, label=label)` (not also `bind_label`, since labels and labeled
assumptions share one namespace and would immediately collide with
themselves); `'arbitrary'` lines go through both `self.context.
bind_arbitrary(name)` (the fresh constant's own name, recovered from the
nullary atomic-formula flag encoding) and `self.context.bind_label(label,
formula)`, since freshness and citability are independent namespaces;
everything else still goes through `bind_label(label, formula)` alone,
alongside the pre-existing `self.formula_by_label`. All three share the
same scope boundary that structure already had: a standalone labeled
subproof block (`(label, 'subproof', body)`) is excluded, since its
"value" isn't a formula.

New method `elaborate_subproof_body(entries)` gives every subproof --
however it's attached (a standalone labeled block, a `rule_below`
justification's immediate subproof, or one of a `rule_hybrid`
justification's several attached subproofs) -- its own child
`ProofContext` *and* child `DeclarationScope` for the duration, mirroring
`ProofValidator._validate_block`'s own `declarations.child()`/
`labels.child()` scoping for the same construct. `self.declarations`
joined `self.context` here once confirmed to already agree on the
underlying policy -- `DeclarationScope.declare()` already walks its full
parent chain via `lookup()` before raising, exactly like `ProofContext.
declare()` -- so unlike labels (next paragraph), there was no policy
question to settle, only an implementation gap. `self.origin_by_label` and
`self.formula_by_label` remain flat/global: both are keyed by full dotted
label strings, unique across the whole proof by construction, so flatness
never risked a collision the way bare symbol/declaration/label names
(freely reused across sibling scopes) did.

`lookup_declaration` (the method `elaborate_compound_declaration`'s carrier
checks call, e.g. "has X been declared yet" for `R be a relation on X`) now
resolves through `self.context.lookup_declaration()` instead of the legacy
`self.declarations.lookup()` -- the declaration half of "resolve
declaration and label references through the context". This was safe
unconditionally, not just empirically: the two structures are seeded,
written, and now scoped identically, so for any name either can currently
answer, they agree by construction, not by coincidence of what the corpus
happens to exercise. Confirmed with a hand-constructed divergence (declare
something directly into `self.context` only, bypassing `register_declaration`
entirely) rather than a corpus fixture, since no real proof can distinguish
the two structures anymore -- see
`test_lookup_declaration_resolves_through_proof_context_not_the_legacy_scope`.
`self.declarations` itself is untouched and still written to (still needed
by `elaborate_proof`'s separate feed into `DiscreteMath.relation_rule_set`,
`context.declarations.declarations_here()` -- a different concern from
resolving a reference, not migrated here).

The *label* half was blocked on one open policy question, now settled:

Resolved: `ProofContext.bind_label` refused to let a label shadow one
already visible in an enclosing scope (see
`test_each_namespace_rejects_duplicates_across_visible_scopes` in
`test_proof_context.py`), while the kernel's own `LabelScope` used to
*permit* that shadowing silently -- a child scope's local dict entry just
overrode the parent's for lookups made from inside it, no error raised.
Settled in `LabelScope`'s favor adopting `ProofContext`'s stricter rule
(the call the note here previously left open, reasoned through directly
in `LabelScope`'s own docstring): subproof line numbers use dot notation,
structurally distinct from every label visible outside that subproof, so
no legitimate proof can ever produce a genuine collision -- a proof
shadowing a line label is a proof error, not a pattern to accommodate.
`LabelScope.__setitem__` now raises `KeyError` on a shadowed label,
surfaced by `ProofValidator` as `CATEGORY_LABEL_SHADOWING`. With both
structures agreeing, `_ElaborationContext.lookup_reference` now resolves
`try_elaborate_existence`'s "Existence from L" citation through
`ProofContext` instead of the flat, never-subproof-scoped
`formula_by_label` dict it used to read directly -- which turned out to
be a real bug fix, not just a migration: the flat dict let a citation
from one subproof branch silently resolve a same-named label left behind
by an unrelated *sibling* branch, whichever happened to elaborate first.
See `test_existence_no_longer_leaks_a_sibling_subproofs_reused_label` in
`test_elaboration.py`, confirmed against the reverted flat-dict lookup.

"Add end-to-end tests proving parent visibility and child non-leakage" is
now fully covered, including the label half:
`test_label_from_an_enclosing_scope_is_visible_to_existence_inside_a_nested_subproof`
covers parent visibility (an existential from an enclosing scope is
still citable via "Existence from L" inside a nested subproof), and
`test_existence_no_longer_leaks_a_sibling_subproofs_reused_label`
(described above) covers non-leakage -- the property this migration
actually needed non-leakage *for*, unlike the other binding kinds, where
non-leakage was only ever a defensive check with nothing yet depending
on it.

"Preserve source origins and existing elaborated core representations"
was never a missing feature so much as an invariant the whole dual-write
approach depends on: every `self.context.*` call added throughout this
migration sits *alongside* `_elaborate_entry_impl`'s existing
`register_origin`/`self.formula_by_label`/return-value construction,
never inside it, so none of it can change what `elaborate_proof` actually
returns. The pre-existing SetTheory-sugar tests
(`test_subset_proof_elaborates_to_ug_then_conditional_introduction`,
`test_synthetic_freshness_failure_maps_back_to_subset_line`) already
exercised this incidentally throughout every commit of this phase, since
"Subset proof below" elaborates through the identical
`self.context`-touching path. `test_proof_context_dual_write_does_not_
disturb_origins_or_core_entry_shape` now pins the property down directly
and explicitly, against a proof exercising every binding kind the
migration touches (declare, arbitrary, a nested `rule_below` subproof) in
one pass, rather than relying only on incidental coverage.

**Phase 2 is now complete.** All seven checklist items above are done;
`ProofContext` is the authoritative source for every declaration and
label reference elaboration resolves, both structures agree on shadowing
policy, and the migration provably didn't disturb origin tracking or the
core entry representation along the way.

### Phase 3 implementation notes

The premise behind this phase didn't survive contact with how real
mathematical proofs actually work: proofs in a file don't share a
lexical context with each other. A later proof cites an earlier one's
*result* by name -- the way a paper cites Theorem 3 -- not by inheriting
its internal scope. So `ProofContext` was never going to span more than
one proof, which leaves only the within-*one*-proof case for a
context-bound theorem/lemma binding to be for: reusing a fact proven
about a locally-arbitrary object for several different concrete
instances later in the same proof.

That case turns out to need no new binding kind at all. It's already
fully expressible with Universal Generalization (wrap the derivation in
a subproof opening with "let X be arbitrary", generalize to
`forall X, ...`) plus Universal Instantiation (instantiate at as many
concrete objects as wanted, as many times as wanted). Confirmed
empirically before concluding this, not just reasoned through: a
locally-arbitrary derivation generalized once and instantiated for two
different objects validates with the existing rule set alone.

`ProofContext.bind_theorem`/`lookup_theorem`/`theorems_here`/
`visible_theorems`/`require_theorem`/`TheoremBinding` have accordingly
been removed entirely rather than wired into anything -- there was
nothing left for them to do once (a) cross-proof reuse was settled as
deliberately *not* sharing a context, which the already-working,
completely separate `promote_theorem`/`TheoremRule` mechanism already
handles (see the "Theorem-to-rule promotion" section of README.md), and
(b) within-proof reuse needed no new binding kind at all. "Dependency and
visibility rules" is consequently moot too -- there is no theorem/lemma
context binding left to have rules for.

The one real gap this phase surfaced: reusing a locally-general fact for
several objects, while never *needing* new machinery, was tedious to
write by hand (Universal Instantiation then Modus Ponens, one pair of
lines per object). `ProofLogic.UniversalModusPonensRule` bundles that
pair into one citable step -- `Universal Modus Ponens from L1, L2` -- the
same convenience `AlgebraRule`/`SymmetryRule`/`TransitivityRule` already
provide over more primitive derivations elsewhere in the kernel.
`tests/testProofs/universal_modus_ponens.txt` proves the same result the
long way and the short way side by side; `UniversalModusPonensRule`'s own
docstring explains why this belongs to the kernel's ordinary
label-citation machinery -- already correctly scoped and timed by
`LabelScope` -- rather than to `ProofContext` at all. This is what
satisfies the checklist's regression-test bullet above: coverage for the
theorem/lemma-reuse *need* this phase was chasing, even though the
mechanism that ended up satisfying it isn't a theorem/lemma binding.

What's left of this phase is only the third checklist bullet, and it's
unrelated to `ProofContext`: `promote_theorem`'s own defaults are worth
deciding deliberately rather than leaving as incidental behavior --

  - it silently promotes only the *last* top-level derived formula as
    "the" theorem, discarding any other top-level fact a proof happens to
    derive along the way, unless the caller passes `conclusion=`
    explicitly;
  - it only generalizes over top-level `OBJECT` declarations, never
    predicates or functions -- deliberately, since
    `ConstantGeneralizingMatcher` substitutes constant terms
    structurally, and generalizing a predicate/function *symbol* would
    need a different, harder mechanism, not a relaxed check here.

This is a small, self-contained decision about one existing function's
defaults, not an architectural question, and doesn't block anything else
in this file -- pick it up whenever it matters for a real proof corpus.

## Phase 4 — remove duplicated lexical bookkeeping

### Phase 4 Audit — COMPLETE

**Audit findings** (see PHASE4_AUDIT.md for detailed analysis):

*Redundancy identified:*
- [x] `_ElaborationContext.declarations` (`pl.DeclarationScope`) is redundant with `_ElaborationContext.context` for all declaration *lookups*. All references already resolve through `ProofContext`.
  - Only write: dual-write in `register_declaration()`
  - Only read: `declarations_here()` at end of elaborate_proof for DiscreteMath.relation_rule_set hook
  - Safe to remove once `ProofContext.declarations_here()` method is exposed

- [x] `_ElaborationContext.formula_by_label` mostly redundant with `_ElaborationContext.context._labels`. Both track label→formula; refactoring would require moving origin info to `LabelBinding`.
  - Lower priority (small dict, not blocking); defer refactoring

*Not redundant (kernel owns these):*
- [x] `ProofValidator.DeclarationScope` is the kernel's own independent copy, not connected to elaboration. Validates declarations during proof checking. Essential to keep.
- [x] `ProofValidator.LabelScope` is the kernel's own independent label tracking during validation. Not redundant with elaboration.
- [x] `_ElaborationContext.origin_by_label` carries source locations through elaboration for error reporting. Not stored elsewhere; essential.
- [x] `ProofContext._assumptions` and `_arbitrary` only tracked by ProofContext; necessary for elaboration.
